# audit-fs-db — RPEL audited-FS live dashboard

Live financial statements (Balance Sheet, P&L) for **Rays Power Experts Ltd.**, rebuilt from the Zoho Books
**Trial Balance** the same way the auditors do, and reconciled line by line against the audited FY 2025-26 statements.

> Keep this repository **private** - it contains customer-level balances and company financials.

## How it works

```
Zoho TB report ─► lib/tb.mjs ─► accounts ─► lib/mapping.mjs (config/mapping.json) ─► buckets ─► lib/fsEngine.mjs ─► FS lines
Zoho AR aging  ─► lib/receivables.mjs (+ config/overrides.fy26.json) ──────────────────────────┤
Zoho ledger of the 11 party accounts ─► lib/gl.mjs ─► lib/vendors.mjs (+ config/party_rules.json,      │
   (+ get_journal for merged rows, Imprest Staff vendor group)        config/party_overrides.fy26.json) ┘
                                                                            lib/reconcile.mjs compares with config/audited.fy26.json
```

* **Buckets, not groups.** Every account goes to one bucket by *account code* (never by Zoho's group - e.g. the deferred-tax
  asset and the bank overdraft are filed under "Liabilities"/"Assets" the wrong way round in Zoho).
  Rules: `accountId > exact code > family`. A non-zero account nobody claims, or two buckets claiming one account, raises an alert.
* **Auditors' reclassifications** are built into `fsEngine.mjs`: freight inward and CHA/logistics go to purchases; stores consumption to
  operating expenses; net FX gain to other income; the debit side of Fines & Penalties to earlier-year tax; purchases = net material cost +
  change in stock; income-tax provision shown net of advance tax and TDS; overdraft with a debit balance is cash.
* **Manual inputs** the Trial Balance cannot show: `config/inputs.fy26.json` (current maturity of car loans, non-current FDs, non-current
  security deposit, the fines reclass). Re-enter these each year-end from the auditors' schedules.
* **Customer hand-netting** (`config/overrides.fy26.json`): the auditors netted 34 customers' advances against their invoices by hand.
  The list is valid only for the 31-Mar-2026 report and is skipped for any other date.
* **Supplier / party layer** (`lib/gl.mjs`, `lib/vendors.mjs`): the auditors show every party NET, so the ledger lines of the 11 party
  accounts are read per contact. Net credit = trade payable (MSME list -> MSME), net debit = advance to suppliers & others (loans and staff
  advances included). Staff (credit balance) go to Outstanding expenses (Imprest). Three kinds of rule, kept apart:
  1. standing rules - `config/party_rules.json` (who is staff, who is MSME);
  2. the auditors' FY26 judgments - `config/party_overrides.fy26.json` (Cyrun & Gurukripa -> retention, R. Mohnot -> outstanding, three
     people kept as payables not staff, two insurers shown gross). Valid for 31-Mar-2026 only, skipped (with an alert) for any other date;
  3. arithmetic - nothing year specific.
  Safety nets: every party account's ledger total must equal the Trial Balance; the placed amounts must equal the ledger net; the party group
  must equal the Trial Balance's own net; stale / missing override entries warn.
* **Zoho quirk handled**: when one journal posts several contacts to the same account, the ledger report merges them into one row and loses the
  per-contact amounts. `mergedTransactionIds()` lists the journals to fetch with `get_journal`; `expandMergedRows()` swaps in their own lines.
  A merged row that cannot be read is kept (so the account still ties) under "untagged" with an alert.

## Live run and cache (`npm run live`)

```
npm run live                    # Redis self-test -> pull from Zoho -> build -> all checks -> compare with audited -> save to Redis -> read back
npm run live -- --no-save       # same, without saving
npm run live -- --from-cache    # show what Redis holds (no Zoho call)
```
* `lib/zohoData.mjs` - one function per Zoho report (TB, AR aging, ledger limited to the party accounts, journals, vendor group). Every answer is checked
  (dates, account filter really applied, all pages present) so a wrong guess about an undocumented parameter stops the run instead of giving wrong numbers.
* `lib/snapshot.mjs` - `buildSnapshot()` makes the whole plain-JSON snapshot (statements, receivables, suppliers, checks, alerts, audited comparison);
  `refreshSnapshot()` adds a lock so two refreshes never run together.
* `lib/cache.mjs` - Upstash over its REST address. **The database is shared with the MIS dashboard**: only GET/SET/DEL/TTL are possible and every key must
  start with `audit-fs:`. Keys: `snapshot:<org>:<fy>:<India date>` (7 days), `latest:<org>:<fy>` (pointer to the newest good one), `ztoken:<org>`
  (Zoho access token, shared between serverless runs), `journal:<org>:<id>` (12 h), `bill:<org>:<id>` (12 h, update-16), `lock:<org>:refresh`. Large values are gzip-compressed and cut into
  parts under 600 KB (the free plan limits one request to about 1 MB).
* A cached journal that no longer agrees with the ledger (someone edited it in Zoho) is detected and read again automatically.
* Typical cost of one refresh: 26 calls (30 since update-16: + 4 bills of HDFC ERGO, see below; **35 since update-17: + the 5 pages of Zoho's stock summary, read on every refresh and not cached; 39 since update-18: + 4 pages of the ledger of Inventory Asset, also read on every refresh and not cached; 44 since update-19: + 5 pages of the item list (the Usage unit), the same way**) (1 TB + 1 aging + 8 ledger pages + 1 ledger page of the advance account + 1 ledger page of the four deposit / PF accounts (update-15) + 1 staff list + the 5 ageing reports: Customer Balance Summary now, at 30-Sep-2025 and at the day before the year, Sales by Customer for each half of the year (update-12 / 14) + the Vendor Balance Summary of update-13: 4 requests of 50 vendors at each of the two dates) + one call per merged journal (38 on the first run, then served from Redis for 12 h) + **up to 40 vendor cards** (the Vendor Codes of update-14: all 166 are known after about 4 refreshes, then a code is read again only after a week), so the first refreshes after update-14 make about 26 + 38 + 40 = 104 calls and take longer; **update-15 adds, on a run with no warm cache, one call per clean-up journal behind the deposit accounts (34 on the FY26 books; kept in Redis for 12 hours like the others, so about once a day)**; **update-16 adds 4 calls on a cold cache, one per bill of HDFC ERGO (`GET /bills/<id>`, also kept 12 hours in Redis, so about once a day too)** **update-20 adds 1 ledger page of the CWIP and IAUD accounts on every refresh and, on an empty cache, one call per journal behind them (137 on the FY26 books; at most 100 new ones per run - `cwip_journal_budget` in `config/settings.json` - and the rest in the continuation that the page starts by itself; then served from Redis for a month)** (the cron / refresh routes allow 60 s).
* Settings that are not secrets live in `config/settings.json` (start of the books, the known party accounts).

## The web app (`npm run dev`)

```
npm install            # once, and after any change to package.json
npm run dev            # http://localhost:3000   (uses the same .env as npm run live)
npm run build          # production build (what Vercel runs)
```
* Pages: **Overview** (balance sheet in T form, profit and loss and cash flow in brief, how far to trust it), **Workbook** (one tab for each sheet of the audited Excel file, in the order of the file, see below),
  **Audit tie-out** (all 47 lines: Zoho vs audited vs difference), **Customers and suppliers** (searchable), **Checks and alerts**. The side panel switches amounts between rupees, lakhs and crores (kept in the browser).
* Pages read the day's snapshot from Redis, so they open instantly. `lib/server.mjs` decides what is shown: *fresh* (today, no errors), *stale* (newest good one is from an earlier day), *flawed* (errors), *empty*.
  On the first visit of a day (or when nothing is saved) the page loads from Zoho by itself (about 30 s, once). It does not auto-retry a flawed run - press Refresh.
* **Refresh** (side panel): refused if today's good snapshot is less than 10 minutes old; after any attempt nobody starts another for 2 minutes. This protects the Zoho daily quota that all dashboards share.
* **Morning job**: `vercel.json` calls `/api/cron` at 00:00 UTC = 05:30 India time. Vercel sends `Authorization: Bearer <CRON_SECRET>`; without `CRON_SECRET` the endpoint is closed on the web.
* **Sign-in** (optional): set `DASH_PASSWORD` (and `DASH_USER`, default `rays`) and the whole site asks for them. Set it on Vercel - the pages show customer-level balances.
* `AUDIT_FS_SNAPSHOT_FILE=reports/live_2025-26.json` shows a saved snapshot without Redis (viewing only, no refresh).
* `AUDIT_FY` picks the year (default 2025-26). A year needs its own `config/inputs.fyYY.json` first.
* Vercel settings to add later: all `ZOHO_*` and `UPSTASH_*` values from `.env`, `CRON_SECRET`, `DASH_PASSWORD`.

## The rest of the booklet (all 34 sheets of the audited workbook)

Every sheet of `Rays_Power_Audited_FS_F.Y.25-26_Final__Absolute_Standalone.xlsx` has its own **tab** on the **Workbook** screen, in the order of the Excel file, like the sheet tabs at the bottom of Excel (**Index** first; the Index is the list of all 34 sheets and how much of each is live). A dot on the tab says how much comes from Zoho Books: filled = live, half = part live, hollow = as signed. The three Notes sheets 3 to 27 (Note 3, Note 4-19, Note 20-27) are kept together on one tab, **Notes 3 to 27**; every other sheet, including Note 1-2, Note-12 MFA and Note 28 (A), (B), (C), has its own tab. To keep more sheets together, or to split the notes again, edit the `tabs` list at the top of `config/workbook.fy26/index.json` (`{"id", "label", "sheets": [ids]}`); a wrong list is reported on the screen, and `npm test` checks it. The old addresses (`/statements`, `/cash-flow`, `/notes`, `/fixed-assets`, `/ratios`, `/tax`) still work: they send you to the right tab. `lib/tabs.mjs` builds the tabs, `app/tabs/` draws what is on them. Nothing here needs more Zoho calls: it is all worked out, on the page, from the day's snapshot (account balances by group, the statement lines) plus last year's audited figures. So `npm run live` does not change.

* **How a figure is built.** `config/notes.fy26.json`, `cashflow.fy26.json`, `assets.fy26.json`, `ratios.fy26.json` and `tax.fy26.json` hold one formula per line, in the small safe language of `lib/expr.mjs` (`+ - * /`, `max`, `min`, `round`; `a:` a Zoho account, `n:` / `r:` an account group, `l:` a statement line, `i:` a year-end input, `c:` a constant, `row:` another row, `x:` / `y:` a note row this / last year, `p:` last year's audited line). Open *made up of* under any line on the Notes 3 to 27 tab to see the accounts behind it.
* **Where the audited figure comes from.** Each line carries the cell of the audited workbook it is compared with (`"ref": "Note 4-19!G105"`) and last year's audited figure. A tick means the live figure is within Rs 5 of the audited one (notes), Rs 10 (cash flow lines), Rs 25 (cash flow subtotals) or two decimals (ratios), because the auditors round line by line.
* **Does the cash flow close?** Yes, by test: cash at the end = cash on the Balance Sheet = Note 17, and the opening cash = last year's audited closing cash.
* **Sheets as signed** are exported once from the workbook into `config/workbook.fy26/` (one JSON per sheet + `index.json`). Where such a sheet carries a total that must agree with a live figure (closing stock, debtors / creditors ageing, additions to fixed assets, CWIP, IT depreciation, ESI-PF, Dep.Calc.), `index.json` lists it as a *tie* and the page compares the two. The tax-portal sign-in details of the "I. Tax Cases" sheet and the company PAN are **not** exported (a test checks this).
* **Line by line against Zoho** (Debtors Ageing, Creditors Ageing, BS Grouping, P&L Grouping and, since update-17, Closing Stock and, since update-20, CWIP). The sheet keeps its signed figures; three columns are added after the value column: *Live (Zoho)*, *Check* and *Difference*. The `live` entry of the sheet in `config/workbook.fy26/index.json` says which column holds the name and the value, where each block starts (by its heading) and which Zoho list it is compared with: `customer`, `account` (every ledger account), `account:<group>+<group>` (only the accounts of those balance-sheet groups of `config/mapping.json`, e.g. `account:car_loans+cash_credit`; this keeps a profit-and-loss account of the same name out, such as the expense "Interest on Car Loan"), or `supplier:<class>+<class>` (classes: trade_payable, trade_payable_msme, advance, retention, outstanding, imprest). A block may name a list of sources (`["account:outstanding_expenses", "supplier:outstanding"]`), and may carry typed helpers: `totalValue` (the column of the block's Total line, when it is not the column of the lines), `lump` (see below), `aliases` (`{"Electricity Bill Payable": "Outstanding Liability"}`: a line whose Zoho account is called something else) and `sums` (`{"Imprest Account": "supplier:imprest"}`: a line that is the total of a whole Zoho list). `lib/overlay.mjs` does the matching:
  * **Agrees** = same name, figure within Rs 1. **Differs** = same name, another figure (the auditors regrouped the line, or the books changed after signing). **Matched by amount** = no line of that name, but a Zoho balance has the same amount and a similar name (or its contact has no name in the data). Where several lines of the sheet share an amount with several Zoho balances (five investments of Rs 1,00,000; CGST and SGST of the same amount), the pairs whose names share the most words go first, and a pair is taken only when nothing else fits it just as well; a tie stays open (*Not in Zoho*) rather than being guessed. **Not in Zoho** = nothing found; the line stays as signed. **Checked in total** = a `tie` of the sheet (`ties` next to `blocks` and `groups`: `{title, lines: [{block, label, nth?, sign?}], zoho: [{source, name, sign?, group?}]}`), or a block with `lump` (the staff imprest advances; security deposits, fixed deposits and accrued interest on them): Zoho holds those lines as one balance (one account, or one entry with no contact), so they are compared together.
  * A Zoho balance is used once. A total gets a live figure only when the sheet's total really is the sum of the lines above it. Zoho balances that no line of the sheet matches are listed under *In Zoho, not on this sheet*.
  * A difference is information; it never counts as a problem of the books (only a check that could not run does).

## Zoho credentials (read-only Self Client)

1. api-console.zoho.in -> Self Client -> copy Client ID + Client Secret into `.env` (copy `.env.example` first).
2. Generate Code with scopes `ZohoBooks.reports.READ,ZohoBooks.contacts.READ,ZohoBooks.accountants.READ,ZohoBooks.settings.READ` (10 minutes).
3. `npm run zoho:token` (paste the code) -> saves ZOHO_REFRESH_TOKEN into `.env`.
4. `npm run zoho:check` -> PASS/FAIL per endpoint, plus a comparison of the live FY26 Trial Balance with the saved snapshot.

`lib/zoho.mjs` caches the 1-hour access token (Zoho allows only 10 new tokens per 10 minutes per refresh token), backs off on HTTP 429
and never prints secrets. The Reports endpoints are not in Zoho's public docs. Confirmed live on 15-Oct-2026 with the read-only scope list above: `/reports/trialbalance`, `/reports/metadata`, `/reports/generalledgerdetails`, `/reports/aragingsummary`, `/reports/apagingsummary` and the vendor-group filter (`/vendors?cf_vendor_group=...`) work (plus contacts, chartofaccounts, journals). Two reports behave differently from the connector copies we saved, and the loader now asks for them correctly (see the comments in `lib/zohoData.mjs`):
* **General Ledger Details** sends the contact's id on every line but NOT its name unless `select_columns` names it (found live 16-Oct-2026: without it every customer in the advance ledger was a 19-digit id). `fetchLedger` therefore asks for `LEDGER_COLUMNS` (date, account_name, contact_name, transaction_details, transaction_type, entity_number, debit, credit); the party (supplier) ledger had been read without it, so its names are fixed by the same change.
* **Trial Balance** needs `select_columns` (account_id, name, account_code, opening_balance, debit, credit, closing_balance); the default live answer carries only net debit / net credit, so every amount would read as zero. `normalizeTB` now refuses an answer without `closing_balance`.
* **Receivables aging** needs `include_manual_journals=true` and `include_credit_notes=true` together with `report_date` / `to_date`; without them it shows 458.9 million for 133 customers instead of the audited 814.3 million for 209. `as_of_date` alone is ignored.
* **Customer Balance Summary** (`/reports/customerbalancesummary`) and **Sales by Customer** (`/reports/salesbycustomer`), added in update-12 for the ageing.
